# 커밋

## 현재 상태

- 브랜치: !`git branch --show-current`
- 변경 파일:
!`git status --short`
- HEAD 대비 변경량:
!`git diff HEAD --stat`
- 최근 커밋:
!`git log --oneline -15`

## 규칙이 충돌할 때의 우선순위

1. **작은 단위로 쪼갠다.** 커밋 수가 늘어나는 것은 문제가 아니다.
2. **커밋마다 빌드가 된다.**
3. **타입이 정확하다.** 타입이 두 개 필요하면 1번으로 돌아가 나눈다.
4. **제목이 짧다.** 제목이 길어지거나 "및"이 들어가면 1번으로 돌아가 나눈다.

## 메시지 형식

```
타입: 제목

본문 (선택)

트레일러
```

- **타입**: `feat` `fix` `refactor` `perf` `style` `test` `docs` `build` `ci` `chore` `revert` 중 하나. 소문자. 스코프(괄호)는 쓰지 않는다.
- **제목**
  - 한국어 명사형으로 끝낸다: `추가`, `수정`, `삭제`, `구현`, `전환`, `분리`
  - 클래스·함수 이름은 원래 표기 그대로 쓴다.
  - 마침표를 붙이지 않는다.
  - 짧을수록 좋다. 50자는 채울 목표가 아니라 넘지 않을 상한이다. 72자는 절대 넘지 않는다.
- **본문**: 코드만 봐서는 **왜** 이렇게 했는지 알 수 없을 때만 쓴다. 무엇을 바꿨는지 반복하지 않는다.
- **트레일러**: 대화에 커밋 트레일러(`Co-Authored-By` 등)가 지정되어 있으면 빈 줄 하나 뒤에 그대로 붙인다.

타입 판정이 애매하면 [reference.md](reference.md)의 판정표와 예시를 읽는다.

## 절차

### 1. 변경 파악

- 변경이 없으면 그렇게 알리고 끝낸다.
- 파일마다 `git diff HEAD -- <파일>`로 내용을 읽는다. 새 파일은 파일을 직접 읽는다.

### 2. 커밋하지 않을 파일 골라내기

아래는 스테이징하지 않고, 마지막 보고에 목록으로 남긴다.

- `.idea/`, `*.iml`, `build/`, `.gradle/`, `.kotlin/`
- `local.properties`, `*.jks`, `*.keystore` 등 비밀 정보가 담길 수 있는 파일
- 줄바꿈만 바뀐 파일: `git diff --ignore-cr-at-eol --quiet -- <파일>`이 종료 코드 0이면 해당

### 3. 커밋 계획 세우기

남은 변경을 논리적 변경 단위로 나누고 순서를 정한다.

- 리팩터링과 동작 변경을 섞지 않는다.
- 포맷 정리(`style`)와 로직 변경을 섞지 않는다.
- 버그 수정(`fix`)과 그 테스트(`test`)는 따로 커밋한다.
- 레이어를 가로지르는 기능은 레이어 순서로 나눈다: api → data model → repository/usecase → UI.
- 의존성 추가(`build`)는 그 의존성을 처음 쓰는 커밋보다 먼저 온다.
- 여러 파일에 걸친 기계적인 변경(이름 변경, 패키지 이동)은 파일이 많아도 하나로 묶는다.
- 한 커밋의 여러 파일이 서로를 참조하면(예: SKILL.md와 그것이 링크하는 파일) 나누지 않는다.
- **순서는 의존 관계를 따른다.** 뒤 커밋의 코드를 참조하는 커밋이 앞에 오면 그 시점에 빌드가 깨진다.

**한 파일 안에 성격이 다른 변경이 섞여 있으면** `git add -p`는 대화형이라 쓸 수 없다. 계획에 이 사실을 적고 확인 단계에서 선택지를 준다: 한 커밋으로 묶기 / 해당 파일 제외 / 사용자가 직접 나누기.

### 4. 계획 확인받기

계획을 표로 보여준다.

| # | 메시지 | 파일 |
|---|---|---|

현재 브랜치가 `main`이면 새로 만들 브랜치 이름도 함께 보여준다. 이름은 `타입/짧은-영문-설명` 형식이고 소문자 kebab-case다. 타입은 계획의 주된 목적을 따른다. (예: `fix/paging-crash`)

그 다음 **AskUserQuestion**으로 진행 여부를 묻는다. 일반 메시지로 묻고 턴을 끝내면 `allowed-tools`의 사전 승인이 사라지기 때문이다.

### 5. 빌드 확인

`.kt`, `.kts`, `.toml`, `.xml`, `.pro` 변경이 포함되어 있으면 커밋하기 전에 전체 변경 상태에서 `./gradlew assembleDebug`를 한 번 실행한다. 실패하면 커밋하지 말고 에러를 보고한 뒤 멈춘다.

중간 커밋은 하나씩 빌드하지 않는다. 대신 3단계에서 의존 순서를 지켜 각 커밋이 빌드되도록 한다.

### 6. 커밋

1. 현재 브랜치가 `main`이면 4단계에서 확인받은 이름으로 `git switch -c <브랜치>`를 실행한다. `main`에는 커밋하지 않는다. 로컬 `main`에 커밋이 쌓이면 다음 PR에 앞 PR의 커밋이 섞인다.
2. 이미 스테이징된 것이 있으면 `git restore --staged -- <파일>`로 내린다. 작업 트리는 건드리지 않는다.
3. 계획의 커밋마다:
   - `git add -- <파일...>`로 **경로를 명시**해서 스테이징한다. `git add -A`, `git add .`는 쓰지 않는다. 삭제된 파일도 경로를 명시하면 스테이징된다.
   - `git diff --cached --name-only`로 스테이징된 목록이 계획과 같은지 확인한다.
   - 메시지는 heredoc으로 넘긴다.

     ```bash
     git commit -F - <<'MSG'
     fix: PokemonPagingSource 네트워크 에러 크래시 수정

     Co-Authored-By: ...
     MSG
     ```
4. 훅이나 커밋이 실패하면 멈추고 보고한다. `--no-verify`를 쓰지 않는다.

### 7. 보고

- 만든 커밋: `git log --oneline <시작 HEAD>..HEAD`
- 커밋하지 않고 남긴 파일과 그 이유
- PR을 올리려면 `/pr`을 실행하라는 안내
